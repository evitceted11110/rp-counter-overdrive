# 《反擊超載》0.3.0 工程重構規格

狀態：已排程，待實作
日期：2026-07-29
負責：Engineer、QA、Audio Director、Game Designer、Visual Director
版本目標：`0.3.0`

## 目的

把現行「四方向自由時間目押 Boss 戰」重構為：

> 以同一節拍時鐘驅動的左、右、空白三軌反擊戰鬥，並在戰後立即進入可形成流派的 Rogue Run 選擇。

本次重構直接回應四項問題：

1. 音樂與攻擊目前各自計時，玩家主要依賴視覺命中環，節奏體感薄弱。
2. `W/A/S/D + Shift + Space` 同時存在，起始認知與操作負擔過高。
3. `KeyboardEvent.key` 受中文輸入法及鍵盤配置影響，`W/A/S/D` 可能無法可靠觸發。
4. 可玩版本只有單場隨機攻擊，尚未把戰後選擇、流派構築與下一戰差異放進遊戲。

`0.3.0` 不以增加 Boss、美術或詞條數量為優先；先建立可擴充且可驗證的節奏戰鬥與 Rogue 最小循環。

## 不可妥協原則

- 玩家在任何戰鬥階段最多只需要理解三個實體輸入：左、右、空白。
- 音樂、攻擊音、視覺撞擊與判定中心必須共享同一時鐘。
- 難度透過節奏型、速度、連段與資訊組合提升，不再增加按鍵。
- 所有戰鬥規則保持純函式與 seed 可重現，不依賴 DOM、Web Audio 或渲染幀率。
- 靜音時仍可完整判讀；音訊提供節奏與預警優勢，但不是唯一資訊來源。
- `1280 × 720` 必須看見完整戰鬥資訊，不產生頁面或面板捲動。
- Rogue 模組必須改變決策或節奏處理方式；只增加固定傷害百分比的模組不得進入首輪。

## 目標架構

```text
Keyboard／Pointer
       │
       ▼
Input Router ──────────────┐
       │                    │
       ▼                    │
純函式 Combat Core         │
       │                    │
       ├── Combat Events ───┼──► Render
       │                    │
       └── Music Commands ──┴──► RhythmTransport ─► Web Audio

Run Core
  ├── 路線
  ├── 核心／模組
  ├── Boss 節奏圖生成
  └── 戰後三選一
```

依賴方向固定為：

- `src/core/**` 不得依賴 `src/input`、`src/audio`、`src/render`。
- 輸入、音訊與渲染只把外部時間或操作轉成 core 可接受的值。
- `RhythmTransport` 擁有播放時鐘，但不擁有傷害、獎勵或勝敗規則。
- Run Core 產生本戰規則與節奏圖；Combat Core 只執行當前戰鬥。

## 一、輸入層

### 公開操作

| 實體輸入 | 遊戲動作 | 預設語意 |
|---|---|---|
| `ArrowLeft` | `left` | 左軌反擊 |
| `ArrowRight` | `right` | 右軌反擊 |
| `Space` | `center` | 中央重拍震返；破防攻擊也以公開的中央目標呈現 |

畫面按鈕與未來控制器輸入也必須轉換成相同的 `left | right | center`，不得直接呼叫傷害函式。

### 鍵盤正規化

新增獨立 Input Router，使用 `KeyboardEvent.code`，不得再以 `event.key` 判斷英文字母。

處理規則：

1. 只在戰鬥已啟動、未暫停、未結算時接受戰鬥輸入。
2. `event.repeat === true` 時忽略，避免長按連續蒙答案。
3. `event.isComposing === true` 或相容事件 `keyCode === 229` 時忽略。
4. 焦點位於 `input`、`select`、`textarea`、`button`、音量滑桿或 `contenteditable` 時不攔截。
5. 只有確認事件會交給遊戲處理時才呼叫 `preventDefault()`。
6. 開始／重新挑戰後，把焦點移到具 `tabindex="-1"` 的戰鬥容器。
7. 切出頁面、開啟音訊設定或暫停層時，清除任何暫存輸入狀態。

`KeyboardEvent.code` 可消除鍵盤配置與輸入語系造成的字元差異，但不能強行取得已被作業系統組字候選介面消耗的事件。因此遊戲區必須主動取得非文字焦點；正在操作表單時則刻意不搶鍵。

### Space 固定語意

空白鍵永遠只產生 `center`，代表命中中央軌的目標拍：

1. 普通中央重拍進入判定窗：執行中央震返。
2. 破防攻擊以紅色中央目標進入判定窗：執行破防反制。
3. 沒有公開中央目標：回傳無效事件，不改變資源與戰鬥結果。

Space 不得在安全時段、空拍或其他情境暗中變成「施放核心」。起始核心全部以被動規則、自動觸發或已公開的節拍條件運作；即使核心把原本的空拍改寫成中央目標，也必須在輸入窗口前把該拍明確顯示為中央軌目標。對玩家而言，Space 的語意始終只有「命中中央拍」。

## 二、三鍵 Combat Core

### 型別重構

以概念型別取代四方向模型：

```ts
type CombatAction = 'left' | 'right' | 'center'
type BeatSubdivision = 1 | 2 | 4
type DifficultyTier = 0 | 1 | 2 | 3

type RhythmAttack = {
  id: string
  action: CombatAction
  kind: AttackKind
  targetBeat: number
  subdivision: BeatSubdivision
  patternId: string
  difficultyTier: DifficultyTier
  counterable: boolean
  seriesIndex?: number
  seriesLength?: number
}
```

實作時可調整名稱，但必須保留「輸入語意、節拍位置、Pattern 身分、難度階段」四類資料，不能只把 `Direction` 刪成兩個值。

### 單一判定入口

`counter()`、`phaseDodge()`、`releaseBrakeCore()` 收斂為：

```ts
resolveAction(state, action, timingOffsetMs)
```

回傳值仍為不可變 `GameState`，並產生可供畫面與音訊消費的領域事件。領域事件至少能區分：

- 太早
- 完美
- 普通
- 錯軌
- 逾時
- 中央重拍
- 破防反制
- 無效輸入

同一攻擊只接受第一次有效判定。輸入事件不可直接觸發音效或改 DOM。

核心觸發是 `resolveAction` 或小節結算後產生的規則結果，不是第四種 action，也不是 Space 的第二條處理分支。領域事件須另行區分核心的被動觸發、自動觸發及節拍條件觸發，供畫面與音訊解釋因果。

### 難度曲線

| 階段 | 可用內容 | 禁止內容 |
|---|---|---|
| Tier 0 | 左右單拍、寬窗口、固定預告 | 切分、連續破防、假動作 |
| Tier 1 | 左右交替、兩拍連段 | 連續三拍、拍外延遲 |
| Tier 2 | 八分切分、休止拍、單次中央重拍 | 相鄰中央重拍、隱藏完整連段 |
| Tier 3 | 切分連段、公開的延遲與回返、左右＋中央組合 | 新按鍵、無預警改軌 |

Pattern 由 seed 生成，但必須從通過可演奏性檢查的 Pattern 庫中選取。禁止逐拍純亂數，避免無法學習或超越人體輸入上限的排列。

### 判定窗口

首輪可沿用普通與完美窗口作測試基線，但窗口必須以 `timingOffsetMs` 相對於節拍撞擊中心計算，不再以某個 render frame 是否跨過命中環判斷。

正式數值由 Gate 3 人類測試決定。工程只保證：

- 60、120、144Hz 得到相同判定。
- 同一偏移值在所有瀏覽器得到相同 grade。
- 視覺掉幀不縮短玩家可輸入的真實窗口。

## 三、共享 RhythmTransport

### 主時鐘

玩家操作解鎖音訊後，以 `AudioContext.currentTime` 作唯一播放主時鐘。`RhythmTransport` 負責：

- BPM 與小節位置。
- 拍、八分、十六分的時間換算。
- 提前排程音樂、攻擊預告與撞擊音。
- 將目標拍轉換成 core 所需的毫秒偏移。
- 暫停、恢復與頁籤隱藏後重新定位。

Render 不再自行決定攻擊何時開始或何時超時，只讀取 Transport 的當前位置繪製命中軌跡。

### 排程規則

- Web Audio 事件至少提前 100ms 排程；排程輪詢可維持約 25ms。
- 畫面依主時鐘內插，不能用累加幀時間推進節拍。
- BPM 改變只在下一小節邊界生效。
- 已排程到 Web Audio 的事件不得因 render 掉幀重複觸發。
- 暫停或 `visibilitychange` 後不得讓玩家在回到頁面時立即承受累積攻擊。
- 音訊無法啟動時，使用同一 Transport 介面切換到 `performance.now()` 降級時鐘；此模式仍可玩，但必須在 QA 記錄節奏誤差。

### 音樂與戰鬥的結合

音樂不再只是依威脅疊加的背景循環：

- 攻擊預告在目標拍之前的固定音樂位置出現。
- Boss 撞擊、判定中心與鼓組重拍／切分點共用時間戳。
- 完美反擊在目標拍補入獎勵聲部，不以輸入當下重新啟動獨立音效。
- 失誤保留拍點但抽掉或失諧下一個節奏層。
- Rogue 模組可要求 Transport 在下一小節加入 Stem、改寫擊中音或標示特殊拍，但不得改寫傷害規則。

音訊 Cue 必須可替換程序式音源與正式素材，不讓 core 知道使用 Oscillator、取樣或音樂 Stem。

## 四、三軌單畫面 UI

### 戰場資訊

中央五個固定鍵位提示改為三條常駐軌：

```text
┌──────────── Boss／節拍／威脅 ────────────┐
│                                           │
│       左軌          中央軌          右軌  │
│        ←          重拍／破防          →   │
│                    命中線                 │
│                                           │
├ 核心 ─ 模組 1 ─ 2 ─ 3 ─ 4 ─ 連段／完整度 ┤
└ 下一 Pattern／鍵位／音訊設定 ─────────────┘
```

- 三軌、當前目標與下一拍必須同時可見。
- 中央軌以顏色與文字區分「普通重拍」及「紅色破防」，不能只改顏色。
- 核心卡只顯示被動條件、進度與自動觸發結果，不提供可按下的主動施放狀態。
- 初階只顯示下一拍；進階連段提前公開完整序列。
- 戰後草稿與路線選擇使用覆蓋層，不改變頁面高度。
- 音訊面板開啟時不得遮住命中線，鍵盤焦點不得流回戰鬥。
- 滑鼠／觸控用三個畫面按鈕與鍵盤共用 Input Router。

### 尺寸基準

硬驗收尺寸：

- 1280 × 720
- 1440 × 900
- 1920 × 1080

三者皆須：

- `documentElement.scrollWidth <= clientWidth`
- `documentElement.scrollHeight <= clientHeight`
- 左、右、空白提示完整可見。
- Boss、玩家完整度、節拍、當前模組與結算入口不互相遮擋。

960px 以下不列入 `0.3.0` 正式支援，但不得因固定最小寬造成正常桌面尺寸水平捲動。

## 五、Rogue Run 接入

### 0.3.0 最小循環

```text
選 1 個起始核心
  → 戰鬥 1
  → 三選一模組
  → 二選一路線
  → 戰鬥 2
  → 三選一模組
  → 戰鬥 3
  → Run 結算
```

此三戰 Run 是六戰正式版的縮短驗證，不是假裝完整內容。

### RunState

Run Core 至少保存：

- run seed 與當前節點。
- 玩家完整度。
- 起始核心。
- 最多四個被動模組。
- 已走路線與已擊敗 Boss。
- 下一場公開的 Boss 節奏標籤。
- 草稿候選與選擇歷史。

所有候選、路線與戰鬥 Pattern 均由衍生 seed 生成；重播同一 seed 與同一選擇歷史必須得到完全相同結果。

### 首輪流派鉤子

P1 至少落地三個可感知家族，每個家族先做兩個模組：

- 交替／連鎖：完美左／右反擊改寫下一拍或自動補入回聲。
- 空拍／中央：核心依已公開的節拍條件，把特定空拍預先改寫成中央目標；玩家仍只是在中央目標按 Space。
- 容錯／未來壓力：失誤後自動保留連段或在下一小節加入公開的中央目標。

舊「相位」資源與 Shift 操作不移植。破防招直接改寫為紅色中央重拍，使用 Space 正面震返。模組效果必須透過 core 的規則 Hook 或資料化 Modifier 實作，不允許在 render 中以模組 id 寫特例，也不得把 Space 重新包裝成主動核心鍵。

### Rogue 驗收問題

完成一個三戰 Run 後，玩家必須能回答：

1. 這局選了哪一種流派。
2. 至少一個模組改變了左／右序列、公開中央目標或失誤恢復方式。
3. 下一條路線的節奏標籤如何影響選擇。
4. 死亡重開後，候選與路線為何不同。

若只能感受到傷害數字增加，Rogue 接入不算完成。

## 六、TDD 實作順序

每一步先寫失敗測試，再完成最小實作；不得先大量改 render 再補 snapshot。

### Phase A：特性鎖定

1. 鎖住現行傷害、威脅、勝敗、seed 重現與音訊解鎖行為。
2. 將預期淘汰的四方向／Shift 測試標記為 migration coverage，不直接刪除。
3. 建立 `0.2.1` 與 `0.3.0` 行為對照表。

### Phase B：輸入路由

1. `code` 對應三個 action。
2. 中文 `key` 不影響 `code` 對應。
3. repeat、composing、表單焦點與非戰鬥狀態均忽略。
4. 只有已處理事件會 `preventDefault()`。
5. Keyboard 與 pointer 產生相同 action。

### Phase C：三鍵 Core

1. `resolveAction` 邊界值與 Space 固定中央語意。
2. 同一攻擊只判定一次。
3. Pattern seed 重現。
4. Tier 0–3 合法內容與可演奏性限制。
5. 核心只能由被動、自動或已公開節拍條件觸發；非中央目標按 Space 不得觸發核心。
6. 舊四方向函式移除前，以對照測試證明必要數值已遷移。

### Phase D：RhythmTransport

1. 拍與毫秒換算。
2. 小節邊界換速。
3. 暫停／恢復定位。
4. 已排程事件去重。
5. 以可注入 Fake Clock 測試，不在單元測試直接依賴真實 AudioContext。

### Phase E：Render 與 Audio 整合

1. 三軌狀態由同一 Transport 時間渲染。
2. 攻擊預告、撞擊音、視覺中心與判定中心共用 event id／時間戳。
3. 靜音與 AudioContext 降級模式仍可完成戰鬥。
4. 單畫面尺寸與焦點路由回歸。

### Phase F：Rogue Run

1. Run seed 與選擇歷史重現。
2. 三選一無重複且符合家族規則。
3. 路線標籤與下一戰 Pattern 一致。
4. 模組 Hook 改變規則而非只改顯示。
5. 勝利、死亡、重開與三戰結算完整。

每個 Phase 均須通過 `pnpm verify` 才能進入下一 Phase。

## 七、QA 測試矩陣

### 瀏覽器與輸入法

人工 Gate 至少涵蓋：

| 平台 | 瀏覽器 | 輸入法 |
|---|---|---|
| macOS | Chrome 最新正式版 | 英文、注音 |
| macOS | Safari 最新正式版 | 英文、注音 |
| macOS | Firefox 最新正式版 | 英文、注音 |
| macOS | Chrome 最新正式版 | 倉頡或拼音其中一種 |

每組確認：

- 從開始按鈕進入後，左、右、空白可連續完成一個 Pattern。
- 輸入法保持中文時不需手動切英文。
- 正在音量滑桿操作時，左右鍵只調音量。
- 關閉音訊面板後，焦點回到戰鬥容器。
- Space 不會重複點擊開始／重新挑戰按鈕。
- 組字狀態不觸發戰鬥，也不破壞候選字操作。

合成 `KeyboardEvent` 只能作單元測試，不能取代以上 OS／IME 人工 Gate。

### 音訊與延遲

- 攻擊撞擊音與判定中心：目標誤差 `< 30ms`，P0 硬上限 `< 50ms`。
- 視覺命中線與判定中心：目標誤差 `< 1 frame`；60Hz 硬上限 `< 33ms`。
- 60、120、144Hz 相同輸入偏移得到相同 grade。
- 主執行緒人工阻塞 100ms 後，已排程音訊不得重複；畫面恢復後須對齊下一個合法節點。
- 頁籤隱藏 3 秒再返回，不得累積傷害或一次播放多個撞擊音。
- 藍牙輸出延遲不作判定補償依據；可在設定中提供音訊／視覺校準值，但判定核心只接受統一校準後的 offset。
- 主輸出不得削波；三條匯流排與全域靜音仍須有效。

### 遊戲公平性

- Tier 0 第一場 10 秒內出現第一次可完成反擊。
- Tier 0 不出現 Space；Tier 1 完成左右教學後，Tier 2 才導入中央重拍。
- 所有多拍 Pattern 在第一拍前揭露完整長度。
- 假動作不得在最後一個公平反應窗口改變軌道。
- 靜音、降低動態、色覺不足模式皆保有非音訊／非單一色彩提示。

## 八、版本遷移

### 版本號

- `0.2.1`：保留為四方向背景音樂版標記。
- `0.3.0`：三鍵節奏與三戰 Rogue Loop，屬破壞性玩法變更。

### 狀態與資料

現行版本沒有本地存檔，因此不需要遷移舊戰鬥中的 `Direction`、`phaseCharges` 或 attack 序列。

若平台 SDK 已保存 run／seed：

- 新增 `schemaVersion: 3`。
- `schemaVersion < 3` 的未完成戰鬥不得嘗試續玩，轉成「舊版挑戰紀錄」並安全開始新 Run。
- 可保留舊 seed 作歷史顯示，但不得宣稱能在新規則下重播相同戰鬥。
- 設定中的音樂、效果、介面音量與全域靜音可以遷移。
- 不得使用 `localStorage`、`sessionStorage` 或 IndexedDB 自行保存；一律透過平台 SDK。

### 文件與可見文字

同一提交必須同步更新：

- `game.json`、`package.json`
- `README.md`
- `SMOKE_TEST.md`
- `design/spec.md`
- `design/audio-guide.md`
- `content/audio-events.json`
- 所有 `W/A/S/D`、`Shift`、四方向與相位舊說明

任何玩家可見位置殘留舊操作，視為 P0 阻擋問題。

## 九、完成判準

### P0：可合併的戰鬥重構

以下全部成立才可稱為「三鍵節奏戰鬥完成」：

- 遊戲只有左、右、空白三個戰鬥輸入。
- 中文輸入法開啟時可操作；人工通過 Chrome、Safari、Firefox 基本 Gate。
- Core 只有單一 action 判定入口；Space 固定只命中中央目標，且有普通中央、破防中央與無目標三類邊界測試。
- 所有核心均為被動、自動或已公開節拍條件觸發；不存在主動核心施放分支。
- 音樂、音效、視覺與判定共用 RhythmTransport。
- 撞擊音與判定中心誤差硬上限小於 50ms。
- 60、120、144Hz 不改變判定 grade。
- Tier 0 能教會三鍵，Tier 1 至少有左右兩拍 Pattern。
- 1280 × 720 無滾動且三軌完整可見。
- 靜音可完成整場戰鬥。
- 頁籤切換與 AudioContext 暫停不造成累積傷害。
- 玩家可見文字沒有 `W/A/S/D`、`Shift` 或舊四方向規則。
- `pnpm verify` 全數通過。

P0 不要求完整 Rogue Run，但其 core 與 UI 必須保留 RunState、模組列及戰後覆蓋層接點。

### P1：可驗證的 Rogue 垂直切片

以下全部成立才可稱為 `0.3.0`：

- 可完成「選核心 → 戰鬥 → 三選一 → 路線 → 戰鬥 → 三選一 → 戰鬥 → 結算」。
- 至少 3 個流派家族、每家族至少 2 個可用模組。
- 至少一個模組改變左／右序列、一個改變公開中央目標的節奏配置、一個改變失誤後策略。
- 路線在選擇前公開下一戰至少兩個節奏／招式標籤。
- 同 seed 加同選擇歷史完整重現。
- 死亡會失去本局 build 並可立即開始新 Run。
- 模組效果由 core Hook／Modifier 執行，render 無模組 id 特例。
- 三戰過程始終維持單畫面或覆蓋層，無頁面滾動。
- 音樂會因戰鬥狀態與至少一個 build 產生可聽見但不破壞判讀的層次變化。
- 完成至少一輪內部人類測試；多數測試者能指出自己的流派與一個被改變的按鍵時機。
- `pnpm verify`、跨瀏覽器 Gate、音訊延遲 Gate 全數通過。

### P2：內容化與發佈準備

P2 不阻擋 `0.3.0` 垂直切片，但進公開發佈前應完成：

- 三戰擴為六戰 10–12 分鐘 Run。
- 3 個 Boss 骨架具可辨識的節奏人格與 Pattern 池。
- 4 個起始核心、12 個被動模組完成平衡。
- 正式鼓組、低音、Stem 或等效高品質音源接入，保留程序式降級方案。
- 提供音訊／視覺延遲校準與降低動態選項。
- 30,000 局 seed 模擬通過勝率、流派差距與集中度門檻。
- 完成回歸測試、授權清單、素材歸屬與正式 smoke test。
- 1280 × 720、1440 × 900、1920 × 1080 視覺 QA 無阻擋問題。

## 十、主要風險與停損

| 風險 | 預防 |
|---|---|
| 只換鍵，仍是目押 | P0 強制共享 Transport 與拍點 Pattern |
| Space 語意被核心特例重新污染 | Core schema 禁止主動核心 action；非中央目標按 Space 永遠無效 |
| 被動核心觸發難以理解 | 觸發條件預先顯示，觸發時由核心卡連線至被改寫的拍點與結果 |
| 正式音樂加入後判定漂移 | 先完成時鐘與可替換 Cue 介面，再製作素材 |
| IME 問題被單元測試誤判為已解 | macOS 三瀏覽器人工 Gate 為 P0 |
| Rogue 模組只變傷害 | P1 要求改變至少三類操作時機 |
| render 再度承擔遊戲規則 | 依賴方向與模組特例測試阻擋 |
| 高速靠縮小反應窗製造 | Tier 以節奏組合增難，保留公平窗口 |

若內部測試仍以「看提示按鍵」描述玩法，或玩家無法感到攻擊落在音樂結構內，應停止增加內容，回到 RhythmTransport 與 Pattern 設計，不得以更快 BPM 或更大音量掩蓋。
